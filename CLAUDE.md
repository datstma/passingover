# Passing Over — project brief

*Where the planes above you are going.*

This is the durable brief for anyone (human or Claude) working in this repo.
Read it first; details live in `docs/`.

## Vision

Passing Over shows the aircraft overhead right now, built for daydreaming
rather than plane-spotting. Other apps answer "what is that?" with callsigns
and altitudes. Passing Over answers "where is that going, and what's it like
there?":

- "SK 945 → Chicago. It's 15:12 there, 9°C and overcast. Landing in 7h 40m."
- The journey as a story: where it left from, how long ago, what it will cross.
- A calm ambient mode for a desktop, a spare tablet or a TV (a free, software
  FlightWall).
- Later, a "daydream log" ("this month, planes over your home went to 61 cities").

## Product principles

- Calm over busy. Few numbers, beautiful typography and motion.
- Nothing that feels like an aviation instrument unless the user opts into a
  "technical" layout.
- Metric by default, imperial available.
- Pure open source: no paid tier, subscriptions or ads (D16).
- Privacy: the user's location never leaves the device except as a query to
  the data sources, and coordinates are rounded to ~1 km first.

## Stack

- **UI:** Flutter 3.47.8 (Dart 3.13.7), one codebase for macOS, Windows, Linux,
  iOS and Android.
- **Core:** Rust 1.99.1 (pinned in `rust-toolchain.toml`), edition 2024. The
  core has no Flutter dependency.
- **Bridge:** flutter_rust_bridge 2.13.0, Native Assets backend (Rust is built
  by `app/hook/build.dart`; no CocoaPods, no Cargokit). See D7.
- **License:** MIT OR Apache-2.0.

## Architecture rules

- **All logic goes in `passingover-core`.** `Sky` does a whole poll for every
  front end (D30). The bridge crate (`app/rust`) only converts types and
  forwards calls; the Flutter app only lays out the text it gets. If
  something is useful to the CLI too, it belongs in core.
- Data sources are pluggable behind traits (`PositionSource`, `RouteSource`,
  `WeatherSource`, …). v1 needs no API keys.
- Be polite to the sources: poll every ~10–15 s, keep the default radius small,
  cache routes, airports and weather, and back off on errors. Send an
  identifying User-Agent. Concrete numbers are in `docs/data-sources.md`.
- Round coordinates to ~1 km before any request leaves the device.
- Location input: device location in the app; manual lat/lon everywhere;
  "pick on map" later.
- Never add a data source without documenting its terms, limits and
  attribution in `docs/data-sources.md` and logging a decision.

## Commands

Rust (from the repo root):

```sh
cargo build --workspace
cargo test --workspace                                  # fixtures only, no network
cargo clippy --workspace --all-targets -- -D warnings
cargo fmt --all
cargo xtask data                                        # build data/ (needs git + network)
cargo run -p passingover-cli -- now --lat 55.68 --lon 12.57
cargo test -p passingover-core -- --ignored             # opt-in live tests (network)
```

Core modules: `geo` (coordinates, `QueryPoint` privacy rounding), `aircraft`,
`position` (sources + `PositionFeed`), `http` (`HttpClient`, `UreqClient`),
`polite` (D15 numbers), `data` (standing data tables), `route` (normalisation,
plausibility, adsbdb, `RouteLookup`), `weather` (Open-Meteo, MET Norway,
`WeatherLookup`), `regions` (Natural Earth countries and seas, "will cross"),
`flight` (overhead, landing and departure estimates, local time), `story`
(sentences and units), `sky` (one poll for every front end), `credits`,
`log` (the daydream log, D38).

Flutter (from `app/`):

```sh
flutter pub get
flutter run -d macos                       # builds the Rust crate via the hook
flutter analyze
flutter test                               # Dart unit/widget tests
flutter test integration_test -d macos     # launches the app, calls into Rust
flutter test integration_test -d macos --dart-define=PASSINGOVER_LIVE=true
                                           # also polls the real sources
```

Keep all integration tests in `integration_test/app_test.dart`: desktop runs
start the app once per file, and a second start fails on Linux and Windows.
Run `cargo xtask data` first if the app should have the bundled route data.

After changing the bridge API in `app/rust/src/api/`:

```sh
cd app && ../.tools/bin/flutter_rust_bridge_codegen generate
```

`scripts/install-tools.sh` installs the codegen tool into `.tools/` (D20). Its
version must match the `flutter_rust_bridge` crate and Dart package.

## CI (local, D18)

There is no GitHub Actions workflow. Before pushing, run:

```sh
scripts/ci.sh            # this Mac, then the Linux and Windows hosts
scripts/ci.sh local      # Rust (fmt, clippy, tests, cargo-deny) + Flutter
                         # (pins, bindings current, analyze, tests, macOS
                         # integration test); needs flutter on PATH
scripts/ci.sh linux      # or: windows — Rust, then Flutter if set up there
scripts/ci.sh setup windows   # install the pinned Flutter SDK on a host (D28)
scripts/ci.sh clean      # remove sources and build output on the hosts
scripts/ci.sh purge      # remove ~/passingover-ci (incl. Flutter SDK) entirely
```

The remote hosts are set in the git-ignored `.ci-hosts.local`
(`PASSINGOVER_CI_LINUX`, `PASSINGOVER_CI_WINDOWS`). Never commit host names;
the repo is public.

## Shared machines

The development and build machines also run other projects in parallel.
Never affect them:

- On remote hosts, everything for this project stays in `~/passingover-ci`.
  No loose files in the home directory; temp files have a `passingover`
  prefix and are removed.
- Toolchains are additive: rustup installs the pinned version alongside the
  others. Never run `rustup default`, `rustup update` or system upgrades, and
  never install shared-named tools globally (use `.tools/`).
- Remote hosts use our own Flutter SDK in `~/passingover-ci/flutter`, never
  a Flutter that another project installed (D28).
- Set env vars such as `CARGO_TARGET_DIR` per command, never globally.
- Mention any system package you install (apt, winget, brew) to the owner.

## Testing rules

- Unit tests use recorded JSON fixtures; no live network in tests.
- One opt-in integration test may hit live sources. It is marked `#[ignore]`
  and runs with `cargo test -- --ignored`.

## Working agreements

- Log every non-trivial choice in `docs/decisions.md` as the next Dn, with a
  one-line rationale. Update `docs/milestones.md` status as work lands.
- Small, reviewable commits with clear messages, on `main`. The remote is
  `origin` → `github.com/datstma/passingover` (public). Run `scripts/ci.sh`
  before pushing, and push only when the owner asks.
- Commits are authored and committed as **Stefan Månsby** (the repo-local git
  identity). No AI co-author trailers (`Co-Authored-By: Claude …`), no
  "Generated with …" lines, and no other AI attribution in commit messages or
  PR descriptions.
- Ask the owner before anything hard to undo, or before installing system-wide
  tooling beyond the usual Rust/Flutter toolchains. If a prerequisite is
  missing (Flutter SDK, Xcode, Android SDK, Rust targets), say exactly what to
  install rather than working around it.
- Toolchain bumps: change `rust-toolchain.toml` and
  `app/rust/rust-toolchain.toml` together (`scripts/ci.sh local` checks),
  and log a decision.
- Generated files (`app/lib/src/rust/**`, `app/rust/src/frb_generated.rs`) are
  regenerated, never hand-edited.
